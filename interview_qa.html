Service selection rationale
Why DynamoDB for metadata — not Aurora or RDS? Selection ▼
The metadata write pattern is simple: one record written per image, independently, with no joins or transactions needed. DynamoDB handles exactly this — high-throughput, isolated single-row writes at low latency.
The decisive reason is native TTL. DynamoDB reads the ttl field and auto-deletes the record at expiry — no cron job, no extra Lambda, no extra failure point. Aurora has no equivalent native row-expiry mechanism.
Aurora is the right choice when you need complex SQL, multi-table JOINs, or ACID transactions. None of those apply here. Using Aurora would mean running a persistent database instance — paying for compute even at zero load — while DynamoDB on-demand scales to zero when idle.
Why Lambda — not ECS or EC2 — for image processing? Selection ▼
The processing trigger is one S3 ObjectCreated event per image upload. Lambda maps directly onto this model: one event = one invocation. There is no persistent work happening between uploads, so a persistent server (ECS task or EC2 instance) would be idle most of the time and still charging.
Lambda auto-scales per invocation with no configuration — 500 simultaneous uploads produce 500 parallel executions, then drop back to zero. ECS can autoscale too, but with more latency and more configuration overhead.
The company's existing code runs unchanged inside a container image in ECR. Lambda supports container images natively, so there is no need to repackage or rewrite anything to deploy on Lambda rather than ECS.
Why self-managed Kafka on EKS — not MSK Serverless? Selection ▼
The brief is explicit: "This Kafka stream has to be managed by the company's engineers." MSK Serverless abstracts the broker layer entirely — engineers can produce and consume messages, but cannot configure broker settings, tune partition counts, or control scaling decisions directly.
EKS keeps Kafka brokers as Kubernetes pods. Engineers have full access to broker configuration, can apply custom resource limits, and control exactly when and how the cluster scales. That level of control is what the brief requires.
MSK would be the right choice if the brief asked for minimal operational overhead. It did not — it specifically asked for engineer control, so the managed option is the wrong trade-off here.
Why S3 for image storage — not EFS or a database blob column? Selection ▼
S3 is the standard AWS object store for binary data at scale. It integrates natively with Lambda via S3 Event Notifications, with Lifecycle rules for automatic deletion, and with SSE-KMS for encryption — all three are required by this design.
S3 Lifecycle rules handle the 7-day hard deletion automatically, with no custom code. No other AWS storage option has an equivalent declarative, per-bucket expiry mechanism that works at this scale.
EFS is a network file system suited for workloads that need POSIX semantics and concurrent file access. Storing binary images in a database blob column would make the 7-day deletion, encryption, and retrieval by Lambda significantly more complex than necessary.
Why use MSK Connect to move data from Kafka to S3 — not a custom consumer? Selection ▼
MSK Connect is a managed connector framework. The S3 Sink connector is a pre-built, maintained component that reads from a Kafka topic and writes to S3 — exactly the job needed here.
Writing a custom Kafka consumer adds code that needs to be written, tested, deployed, monitored, and maintained. MSK Connect eliminates that entirely — the connector is configured, not coded.
The only reason to write a custom consumer would be if the transformation logic between Kafka and S3 was complex enough that the connector couldn't handle it. For raw image bytes being sinked to S3, the connector is sufficient.
Security
Why SSE-KMS with a Customer Managed Key for the raw bucket — not SSE-S3? Security ▼
Raw images are the most sensitive data in this pipeline — they are the original, unprocessed files from users. SSE-S3 (AES-256 with an AWS-managed key) provides encryption at rest, but the key is entirely controlled by AWS.
A Customer Managed Key gives the company an emergency control: revoking the key makes every object encrypted with it immediately unreadable, even if the S3 bucket itself is accessible. This is a compliance and incident-response capability that SSE-S3 cannot provide.
The processed bucket uses SSE-AES256 (AWS-managed) because the processed data is less sensitive — the highest-risk original is already protected by CMK in the raw bucket, and using CMK everywhere would increase cost and operational complexity without proportional security gain.
Why does Lambda use VPC Endpoints instead of going via the public internet? Security ▼
Lambda runs in a VPC private subnet with no internet gateway. Without VPC Endpoints, calls to S3 and DynamoDB would have to leave the VPC, traverse the public internet, and re-enter AWS — even though both services are AWS-internal.
VPC Endpoints keep traffic entirely within the AWS network. The image data never touches a public IP address at any stage of processing, which reduces the attack surface and satisfies the "security of data in transit" requirement.
VPC Endpoints also remove the need for a NAT Gateway for these service calls, which reduces cost and simplifies the network topology.
What is the specific IAM policy for the Lambda function — can you give the exact permissions? Security ▼
The Lambda execution role has exactly three permissions, each scoped to one specific resource:
s3:GetObject — raw bucket only
s3:PutObject — processed bucket only
dynamodb:PutItem — ImageMetadata table only
No wildcards on Action, no wildcards on Resource. The function cannot read the processed bucket, cannot delete anything from either bucket, and cannot read any DynamoDB records — only write new ones. This is verified by mapping every boto3 API call in the handler code to its corresponding IAM statement.
How are Kafka credentials protected — and what happens if they leak? Security ▼
Kafka broker connections use SASL/TLS — mutual authentication and encryption in transit. The credentials (username/password or certificates) are stored in AWS Secrets Manager, not embedded in any configuration file or environment variable.
At pod startup, the credential is injected from Secrets Manager into the pod's environment. It is never written to disk or committed to any repository. If a credential leaks, it can be rotated in Secrets Manager immediately — the pods pick up the new credential on their next restart without any code change.
Compliance · 7-day purge
Walk me through exactly how the 7-day purge works — all three mechanisms. Compliance ▼
There are three independent mechanisms, each covering a different data store:
1. S3 raw bucket — Lifecycle rule: hard DELETE on day 7. Object versioning is disabled so no shadow copies survive the deletion.

2. S3 processed bucket — same Lifecycle rule applied independently. A failure in one bucket's rule does not affect the other.

3. DynamoDB TTL — Lambda writes a ttl field equal to upload_time + 7 days as a Unix epoch integer. DynamoDB's native TTL feature reads this field and auto-deletes the record at expiry — no cron job, no code.
The three mechanisms are independent on purpose. If one fails, the other two still enforce the deadline. This is defense in depth applied to data retention, not just security.
DynamoDB TTL doesn't delete immediately — there can be a delay of up to 48 hours. Is that a problem? Compliance ▼
This is a known characteristic of DynamoDB TTL — AWS processes deletions in the background, typically within 48 hours of the TTL timestamp passing. The record is expired immediately (Scan and Query exclude it from results once TTL passes), but the physical deletion takes time.
If the compliance requirement is "data must be inaccessible after 7 days" — TTL satisfies that, because expired items are excluded from query results from the moment the TTL timestamp passes. If the requirement is "data must be physically deleted on exactly day 7" — a compensating Lambda sweep would be needed to cover the gap.
For this design, I've treated "purged" as meaning inaccessible rather than physically deleted on the exact second. If the compliance team requires physical deletion within a hard window, that assumption would need revisiting.
Why is S3 versioning disabled on both buckets? Compliance ▼
This is a deliberate trade-off in favor of compliance over recoverability. If versioning were enabled, deleting an object via a Lifecycle rule would create a delete marker rather than permanently removing the data — the actual bytes would still exist in S3 as a previous version.
The brief requires data to be "purged for compliance and privacy." A versioned delete that leaves recoverable data would undermine that requirement. Disabling versioning means the Lifecycle rule produces a true hard deletion — the data is gone and cannot be recovered.
The trade-off accepted here is that there is no recovery path if data is accidentally deleted before 7 days. That is the correct trade-off when privacy compliance is the priority.
Scaling · cost
How does this design scale to handle a sudden spike in image uploads? Scaling ▼
Each layer scales independently and automatically:
API Gateway — managed, no configuration needed for scaling.

Lambda — one invocation per S3 event. AWS scales Lambda executions in parallel automatically, up to the account concurrency limit (can be raised on request).

DynamoDB on-demand — scales read/write capacity automatically with no provisioned throughput to pre-set.

EKS + Cluster Autoscaler — adds EC2 nodes when Kafka broker pods are under pressure; removes idle nodes to control cost.
The design has no single bottleneck that requires manual intervention during a spike. Each component adjusts to actual load rather than a capacity estimate made at deployment time.
How does the design keep costs low when there is low or zero traffic? Cost ▼
The design uses serverless or on-demand pricing wherever stateless components allow:
Lambda — zero cost at zero invocations. No idle compute.

DynamoDB on-demand — zero read/write cost at zero requests. No provisioned capacity to pay for.

Athena — pay per query, per byte scanned. No queries = no cost.

EKS Spot Instances — Kafka brokers on Spot capacity where interruption is tolerable, at 60–70% lower cost than on-demand EC2.
The one component that runs continuously regardless of traffic is EKS (Kafka needs persistent brokers). This is an accepted cost because the brief requires the Kafka stream to be always available and engineer-managed — it cannot be replaced with a serverless option without losing that control.
Why no multi-region disaster recovery? Availability ▼
This is a documented assumption, not an oversight. The design uses multi-AZ within ap-southeast-1 — three availability zones provide protection against a single data center failure, which covers the majority of real-world outage scenarios.
Multi-region DR adds significant complexity and cost: cross-region replication for S3, DynamoDB Global Tables, Route 53 failover policies, and ongoing replication costs. For a data pipeline with a 7-day retention window, the recovery complexity of a full regional outage is disproportionate to the benefit.
If the brief had specified an RTO/RPO requirement that could only be satisfied by multi-region, the design would need to change. With no SLA defined, single-region multi-AZ is the right trade-off between availability, cost, and operational complexity.
BI layer · analytics
What exactly can analysts query in Layer 6 — what data is available? BI ▼
Analysts query the structured metadata that Lambda writes per image: image_id, original_key, processed_key, file_size_bytes, width, height, uploaded_at, and ttl.
This metadata is the structured representation of each image's analytically useful attributes. Athena cannot meaningfully query binary image pixels, but it can query the metadata that describes every image — dimensions, sizes, upload times, volumes. That is what "analytical computation on the data stored" means in this context.
Analysts access this through QuickSight dashboards: upload trends over time, average image dimensions, total storage consumed per day — all derived from the metadata via Athena SQL, with no direct access to AWS console or raw S3 objects.
Why Athena instead of connecting QuickSight directly to DynamoDB? BI ▼
DynamoDB is optimized for low-latency single-record access — it is the right tool for real-time lookup ("what is the status of image X?"). It is not designed for the aggregation and analytical queries that BI requires ("how many images were uploaded per day last week?").
Athena queries S3 using SQL at scale, with columnar Parquet format and date partitioning to keep query cost and latency low. Running aggregations directly against DynamoDB via Scan operations would be expensive, slow, and would consume read capacity from the same table that Lambda uses for writes — competing for throughput.
The two paths serve different purposes: DynamoDB handles real-time operational queries; Athena handles analytical batch queries. Keeping them separate means neither interferes with the other's performance.
How do analysts access QuickSight — and what prevents them from modifying data? BI ▼
Analysts log in via IAM Identity Center (SSO) — single sign-on using their existing company identity, no separate AWS credentials required. This is the "securing access as the company expands" requirement applied to the analytics layer.
Their IAM permission set is strictly read-only:
athena:StartQueryExecution
s3:GetObject on the analytics bucket only
glue:GetTable

They cannot write to any S3 bucket, cannot delete any data, and cannot access the raw or processed buckets directly.
QuickSight itself handles dashboard rendering — analysts see charts and tables, not raw SQL or S3 paths. The only way they interact with the data is through the pre-built dashboard views.
