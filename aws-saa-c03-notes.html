QUESTION 01 · IAM & Security
一家公司的 Lambda 函数需要读取 DynamoDB 表的数据。下列哪种方式是最安全的 best practice？
  • A在 Lambda 代码中硬编码 Access Key 和 Secret Key
  • B为 Lambda 函数创建一个 IAM Role，附加允许读取 DynamoDB 的 Policy
  • C将 Access Key 存储在 Lambda 环境变量中
  • D使用 DynamoDB 的 Public Access 设置允许任何人访问
✓ 答案：B

IAM Role 是给 AWS 服务（如 Lambda、EC2）授权的最佳实践。Lambda 执行时会自动获取临时凭证，无需在代码中管理任何 Key。

A 错：硬编码 Key 是严重安全风险，泄露后难以撤销
C 错：环境变量比硬编码稍好，但 Key 仍需管理轮换，不如 Role
D 错：公开访问违背最小权限原则
QUESTION 02 · RDS / Database
一个电商网站的 RDS MySQL 数据库读取负载很高。架构师想在不停机的情况下提升读取性能，同时保持现有的写入能力。最合适的方案是什么？
  • A启用 RDS Multi-AZ，将读流量分担到 standby 实例
  • B创建 RDS Read Replicas，将应用的读请求指向 Read Replica
  • C升级 RDS 实例类型到更大的规格
  • D将数据库迁移到 DynamoDB
✓ 答案：B

Read Replica 专门用于分担读流量。应用修改连接字符串，读操作走 Read Replica，写操作走主库。

A 是经典陷阱：Multi-AZ standby 实例不可读，只是故障切换备份，无法分担读流量
C：升级实例可以提升性能，但成本高且无法水平扩展，不如加 Read Replica
D：迁移到 DynamoDB 是大工程，且改变了数据库类型，不是"不停机"的好选择
QUESTION 03 · Storage
一家公司每天产生大量日志文件，日志在最初 30 天频繁访问，之后很少访问但需要保留 7 年供合规审计。要求最低成本。最佳方案是什么？
  • A所有文件存储在 S3 Standard，7 年后删除
  • B所有文件存储在 S3 Standard-IA
  • C使用 S3 Lifecycle Policy：前 30 天 Standard，之后转 Glacier Deep Archive，7 年后删除
  • D将日志存储在 EBS 上，7 年后手动删除
✓ 答案：C

Lifecycle Policy 是处理这类"热→冷→删除"场景的标准方案。
Glacier Deep Archive 是 AWS 最便宜的存储类，非常适合 7 年合规归档。

A：全程 Standard 成本高，不必要
B：Standard-IA 取回费高，且不够便宜，不适合 7 年归档
D：EBS 比 S3 贵很多，也不是日志归档的合理方案
QUESTION 04 · Networking
一个应用部署在私有子网（Private Subnet）的 EC2 上，需要访问互联网下载软件更新，但不能被外部主动访问。应该如何配置？
  • A给 EC2 分配公网 IP，直接通过 Internet Gateway 访问
  • B在公共子网中部署 NAT Gateway，私有子网路由表指向 NAT Gateway
  • C使用 VPC Peering 连接到另一个有网络的 VPC
  • D将 EC2 移到公共子网
✓ 答案：B

NAT Gateway 就是为这个场景设计的：允许私有子网内的实例发起出站互联网流量，但阻止外部主动入站连接。
NAT Gateway 部署在 Public Subnet，私有子网的路由表需要有 0.0.0.0/0 → NAT Gateway 的路由。

高可用提醒：每个 AZ 部署一个 NAT Gateway，避免单点故障
A：给私有子网 EC2 公网 IP 会破坏隔离性，不符合需求
D：移到公共子网同样破坏隔离设计
QUESTION 05 · Messaging
一个电商平台在订单创建后需要同时触发：发邮件给用户、更新库存系统、推送到分析系统。这三个系统相互独立。最合适的架构是？
  • A在订单服务中串行调用三个系统的 API
  • B使用 SQS 队列，三个系统都从同一个队列消费
  • C使用 SNS Topic，三个系统各订阅一个 SQS 队列，SNS 发布后 Fan-out 到三个队列
  • D使用 Kinesis Data Streams，三个系统各自读取流数据
✓ 答案：C

这是经典的 SNS + SQS Fan-out 模式。SNS 将消息推送到多个 SQS 队列，每个系统独立消费自己的队列，实现完全解耦。

A：串行调用耦合严重，一个系统故障影响全部，也会增加响应时间
B：SQS 是竞争消费——消息只被一个消费者取走，不能同时给三个系统
D：Kinesis 适合流数据分析，不是这种简单的事件分发场景；且运维复杂度高
QUESTION 06 · Compute
一家公司每周日凌晨 3 点运行一个数据处理任务，通常需要 2 小时，任务可以在中断后重新运行。为了最大化成本节省，应该选哪种 EC2 实例？
  • AOn-Demand Instance
  • BReserved Instance (1-year)
  • CDedicated Instance
  • DSpot Instance
✓ 答案：D

题目两个关键信息：①可以中断后重新运行（fault-tolerant）②最大化成本节省。这完美匹配 Spot Instance 的使用场景，可节省高达 90%。

A：On-Demand 最灵活但也最贵
B：Reserved 适合 7x24 稳定长期负载，每周只用一次不划算
C：Dedicated 用于合规/BYOL 场景，最贵
QUESTION 07 · Security
安全团队发现 S3 存储桶中可能存储了用户的个人身份信息（PII），需要自动扫描并告警。应该使用哪个 AWS 服务？
  • AAmazon GuardDuty
  • BAmazon Inspector
  • CAmazon Macie
  • DAWS Config
✓ 答案：C

Amazon Macie 专门用于发现和保护 S3 中的敏感数据，包括 PII（个人身份信息）。它使用机器学习自动分类数据。

A GuardDuty：威胁检测，分析 VPC Flow Logs / CloudTrail / DNS，不扫描 S3 数据内容
B Inspector：扫描 EC2 / ECR / Lambda 的安全漏洞，不看 S3 数据
D AWS Config：记录资源配置变更，合规审计，不分析数据内容
QUESTION 08 · High Availability
一个 Web 应用需要在 us-east-1 区域实现高可用，跨多个 AZ 部署 EC2。私有子网中的 EC2 需要访问互联网。为确保 AZ 级别的故障不影响互联网访问，应该怎样部署 NAT Gateway？
  • A在一个公共子网部署一个 NAT Gateway，所有 AZ 共用
  • B在私有子网部署 NAT Gateway
  • C在每个 AZ 的公共子网各部署一个 NAT Gateway，每个 AZ 的路由表指向本 AZ 的 NAT Gateway
  • D使用 NAT Instance 替代 NAT Gateway
✓ 答案：C

NAT Gateway 是 AZ-bound（绑定到 AZ），如果只在一个 AZ 部署，该 AZ 故障时其他 AZ 的私有子网也会失去互联网访问。
最佳实践：每个 AZ 一个 NAT Gateway，各 AZ 路由表指向本 AZ 的 NAT Gateway。

A：共用一个 NAT Gateway 是单点故障，该 AZ 挂了所有人都断网
B：NAT Gateway 必须在 Public Subnet（需要通过 IGW 出网）
D：NAT Instance 是过时方案，需要自己管理，不推荐
QUESTION 09 · Database
一个应用使用 DynamoDB，读取操作延迟需要从毫秒级降低到微秒级以提升用户体验。最合适的方案是？
  • A启用 DynamoDB Global Tables
  • B在 DynamoDB 前面部署 DAX (DynamoDB Accelerator)
  • C使用 ElastiCache Redis 缓存 DynamoDB 查询结果
  • D切换到 Aurora，使用 Aurora Read Replica 分担读流量
✓ 答案：B

DAX（DynamoDB Accelerator）是 DynamoDB 的原生内存缓存，提供微秒级读取延迟，与 DynamoDB API 完全兼容，应用代码改动极小。

A：Global Tables 是跨 Region 多活，不降低延迟（反而可能增加复杂度）
C：Redis 也能缓存，但需要额外的应用层代码维护缓存一致性，DAX 更简单且是 DynamoDB 原生方案
D：换数据库类型是大改造，不必要
QUESTION 10 · Architecture Design
一家公司的 Lambda 函数需要访问 VPC 内的 RDS 数据库。随着并发 Lambda 调用增加，RDS 出现了"too many connections"错误。如何在最少代码改动的情况下解决？
  • A增加 RDS 实例大小（scale up）
  • B在 Lambda 代码中实现连接池
  • C在 Lambda 和 RDS 之间添加 RDS Proxy
  • D将 RDS 替换为 DynamoDB
✓ 答案：C

RDS Proxy 是专门解决这个问题的方案：它维护一个到 RDS 的连接池，Lambda 连接 RDS Proxy，RDS Proxy 复用少量真实数据库连接。
"最少代码改动"是关键词——只需修改连接字符串指向 RDS Proxy 端点。

A：Scale up 治标不治本，Lambda 并发增加时问题依然存在
B：Lambda 是无状态的，每次冷启动都是新实例，Lambda 中的连接池无效
D：换数据库类型改动太大，不满足"最少代码改动"
