Service selection rationale
Why DynamoDB for metadata — not Aurora or RDS? Selection ▼
Simple single-row writes + native TTL = no contest.
  • Native TTL — auto-deletes at expiry; no cron, no extra Lambda
  • No JOINs needed — Aurora's SQL power is wasted here
  • On-demand pricing — zero cost at zero load (Aurora always charges for the instance)
Why Lambda — not ECS or EC2 — for image processing? Selection ▼
One S3 event = one Lambda invocation. No persistent compute needed.
  • Auto-scales instantly — 500 uploads → 500 parallel executions, no config
  • Zero idle cost — no traffic, no charge
  • Runs existing container — Lambda supports container images from ECR natively
Why self-managed Kafka on EKS — not MSK Serverless? Selection ▼
Brief says "managed by engineers" — MSK Serverless removes that control.
  • EKS = full broker access — partition counts, resource limits, scaling decisions
  • MSK Serverless = black box — produce/consume only, no broker config
  • If brief asked for "minimal ops overhead" → MSK wins. It didn't.
Why S3 for image storage — not EFS or a database blob column? Selection ▼
S3 is the only option with native Lifecycle deletion + SSE-KMS + Lambda event trigger — all three required.
  • Lifecycle rules → hard DELETE on day 7, declarative, no custom code
  • EFS = POSIX file system, wrong tool for binary blob storage
  • DB blob = makes encryption, deletion, and Lambda retrieval far more complex
Why MSK Connect to move Kafka → S3, not a custom consumer? Selection ▼
Pre-built S3 Sink connector = configured, not coded. Zero custom code to maintain.
  • Custom consumer adds: write → test → deploy → monitor → maintain
  • MSK Connect replaces all of that with config
  • Custom consumer only justified if transformation logic is too complex for the connector (it isn't here)
Security
Why SSE-KMS with Customer Managed Key for raw bucket — not SSE-S3? Security ▼
CMK gives an emergency kill switch: revoke the key → data instantly unreadable, even if bucket is accessible.
  • SSE-S3 = encryption yes, but key is AWS-controlled — no revocation lever
  • CMK = compliance + incident-response capability SSE-S3 cannot match
  • Processed bucket uses SSE-AES256 (lower risk, CMK everywhere = cost + complexity not worth it)
Why does Lambda use VPC Endpoints instead of the public internet? Security ▼
Image data never touches a public IP — stays entirely within the AWS network.
  • Lambda in private subnet → without endpoints, S3/DynamoDB calls exit to the public internet (even though they're AWS services)
  • VPC Endpoints = private routing, reduced attack surface
  • Bonus: removes the need for a NAT Gateway → lower cost + simpler topology
What is the exact IAM policy for the Lambda function? Security ▼
Three permissions, each scoped to exactly one resource. No wildcards anywhere.
s3:GetObject — raw bucket only
s3:PutObject — processed bucket only
dynamodb:PutItem — ImageMetadata table only

Cannot read processed bucket · cannot delete anything · cannot read DynamoDB records
How are Kafka credentials protected — and what if they leak? Security ▼
Credentials live in Secrets Manager, injected at pod startup — never on disk, never in code.
  • SASL/TLS = auth + encryption in transit
  • If leaked: rotate in Secrets Manager → pods pick up new secret on next restart, zero code change
Compliance · 7-day purge
Walk me through exactly how the 7-day purge works — all three mechanisms. Compliance ▼
Three independent mechanisms — if one fails, the other two still enforce the deadline.
1. S3 raw bucket — Lifecycle rule: hard DELETE day 7 (versioning disabled)

2. S3 processed bucket — same Lifecycle rule, applied independently

3. DynamoDB TTL — Lambda writes ttl = upload_time + 7 days (Unix epoch); DynamoDB auto-deletes natively, no cron needed
DynamoDB TTL can delay up to 48 hours — is that a compliance problem? Compliance ▼
Expired items are excluded from all queries the moment TTL passes — they're inaccessible, even if not yet physically deleted.
  • "Inaccessible after 7 days" → TTL satisfies this
  • "Physically deleted on exactly day 7" → need a compensating Lambda sweep
  • This design assumes inaccessible = purged; would revisit if compliance team requires physical deletion
Why is S3 versioning disabled on both buckets? Compliance ▼
Versioning on = Lifecycle rule creates a delete marker, not a true deletion. Data survives as a prior version.
  • Brief requires data "purged for compliance and privacy" → versioned delete undermines that
  • Versioning off = Lifecycle produces a hard, unrecoverable deletion
  • Trade-off: no recovery path for accidental early deletion — correct trade-off when privacy is the priority
Scaling · cost
How does this design handle a sudden spike in image uploads? Scaling ▼
Each layer scales independently and automatically — no manual intervention, no single bottleneck.
  • API Gateway — managed, scales automatically
  • Lambda — parallel invocations per event, up to account concurrency limit
  • DynamoDB on-demand — auto-scales read/write capacity
  • EKS + Cluster Autoscaler — adds/removes EC2 nodes based on Kafka pod pressure
How does the design keep costs low at zero or low traffic? Cost ▼
Serverless/on-demand everywhere stateless — pay only for actual usage.
  • Lambda — zero cost at zero invocations
  • DynamoDB on-demand — zero cost at zero requests
  • Athena — pay per query/byte scanned; no queries = no cost
  • EKS Spot Instances — Kafka on Spot = 60–70% cheaper than on-demand
  • EKS runs 24/7 (Kafka needs persistent brokers) — only accepted always-on cost
Why no multi-region disaster recovery? Availability ▼
Deliberate trade-off: multi-AZ covers most real outages; multi-region complexity is disproportionate for a 7-day-retention pipeline with no defined RTO/RPO.
  • 3 AZs in ap-southeast-1 = protection against single data centre failure
  • Multi-region cost: cross-region replication, DynamoDB Global Tables, Route 53 failover, ongoing replication fees
  • If brief had specified RTO/RPO → design changes. It didn't.
BI layer · analytics
What exactly can analysts query in Layer 6? BI ▼
Structured metadata — not raw pixels. Athena queries what describes each image, not the image itself.
Fields per image: image_id, original_key, processed_key, file_size_bytes, width, height, uploaded_at, ttl

QuickSight dashboards: upload trends, avg dimensions, total storage/day — all via Athena SQL, no raw S3 access
Why Athena — not QuickSight directly to DynamoDB? BI ▼
DynamoDB = low-latency single-record lookup. Athena = SQL aggregations at scale. Different tools for different jobs.
  • DynamoDB Scan for analytics = expensive, slow, competes with Lambda's write throughput
  • Athena queries S3 Parquet with date partitioning → cheap + fast
  • Two paths, zero interference: DynamoDB for real-time ops, Athena for batch analytics
How do analysts access QuickSight — and what prevents data modification? BI ▼
SSO via IAM Identity Center. Read-only IAM permissions. Analysts see dashboards — not SQL, not S3 paths.
Permissions granted:
athena:StartQueryExecution
s3:GetObject — analytics bucket only
glue:GetTable

Cannot write to any S3 bucket · cannot delete data · cannot access raw or processed buckets
