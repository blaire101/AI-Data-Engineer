Redshift Deep Dive

Distribution Style

  • AUTOAutomatic selection: small tables use ALL, large tables use KEY. Recommended for beginners.
  • EVENRound-robin even distribution. For non-Join scenarios, prevents data skew.
  • KEYDistribute by specified column. Same column values land on same node during Join, reducing network transfer.
  • ALLFull copy on each node. Suitable for small dimension tables (Join optimization).
Classic Large Table Join Pattern: Large table uses KEY (customer_id), small dimension table uses ALL → Co-located Join with zero network transfer.

Other Key Features

  • Sort KeyDetermines data order on disk, accelerates range queries
  • WLMWorkload Management: allocates query resources by user group
  • COPY CommandBatch load from S3 — fastest method (parallel)
  • UNLOADExport Redshift → S3, can specify Parquet format
  • Materialized ViewsPre-computed results, accelerates repeated aggregation queries
  • SpectrumQuery S3 external tables, hot/cold data separation architecture
  • ServerlessBilled by RPU-hour, no cluster management needed
Athena Query Optimization (Cost + Performance)
  • Use Parquet/ORCColumnar format, only scans needed columns — most effective cost reduction
  • PartitioningPartition by year/month/day; WHERE clause skips irrelevant partitions
  • CTASWrite query results as a new Parquet table, speeds up subsequent queries
  • WorkgroupControls scan limit per team, prevents budget overruns
  • Federated QueryCross-data-source queries (RDS/DynamoDB) via Lambda Connector
  • MSCK REPAIR TABLEUpdates Glue Catalog partitions so Athena can discover new partitions
Athena bills per GB scanned: Parquet + Partitioning = the optimal combination for cost savings and speed.
Lake Formation Access Control
  • Data CatalogUnified metadata (populated by Glue Crawler)
  • Database-level GrantGrant a role access to an entire database
  • Table-level GrantGrant a role access to specific tables
  • Column FilterHide or mask certain columns for specific roles (PII protection)
  • Row FilterShow only rows matching a condition for specific roles
  • IAM + LF Dual CheckBoth must allow access — if either denies, access fails
Lake Formation Permission Model: IAM Policy AND Lake Formation Grant must both be satisfied! Configuring only one is not enough.

EMR Cluster Configuration Key Points

Node Types

  • Master NodeManages cluster, YARN/HDFS NameNode — must be On-Demand
  • Core NodeRuns tasks + stores HDFS — prefer On-Demand
  • Task NodeRuns tasks only, no HDFS storage — can use Spot (save 90%)

Storage Options

  • EMRFS (S3)Recommended: persistent, data survives cluster termination
  • HDFS (Local)High performance but temporary — data lost when cluster terminates
  • EBSLocal disk for intermediate computation results

Cost Optimization

  • Transient ClusterAuto-terminate after task completes, pay only for active hours
  • Task Node SpotUse Spot for Task Nodes to save 70–90%
  • Instance FleetMix multiple instance types to improve Spot availability
EMR Task Node Spot is Best Practice: Task Nodes don't store HDFS data — if Spot is reclaimed, only the task retries; data is safely in S3 (EMRFS).

Q01 · Domain 1 Real-Time Stream Processing
An e-commerce platform needs to analyze user clickstreams in real time (50,000 events/second), compute the top 10 trending products per minute, and write results to DynamoDB for API queries. What is the most appropriate architecture?
  • AKinesis Firehose → S3 → Glue ETL (triggered hourly) → DynamoDB
  • BSQS → Lambda (triggered every minute) → DynamoDB
  • CKinesis Data Streams → Kinesis Data Analytics (Flink) window aggregation → Lambda → DynamoDB
  • DMSK → EMR Spark Streaming → Redshift
✓ Answer: C

Requirements: real-time processing (millisecond-level) + window aggregation (top 10 per minute) + low-latency queries (DynamoDB).
Kinesis Data Streams ingests high-throughput real-time data → Kinesis Data Analytics (Flink) performs sliding window aggregation → Lambda writes to DynamoDB.

A is wrong: Firehose has a 60s buffer; Glue triggered hourly is not real-time
B is wrong: SQS cannot do streaming window aggregation; Lambda periodic trigger is not real-time
D is wrong: MSK + EMR is heavy; Redshift is not suitable for API low-latency point queries
Q02 · Domain 1 Format Optimization
A large number of JSON logs are stored in S3. Athena queries are slow and expensive. Analysts query only the last 7 days of data each day. How can you most effectively reduce cost and improve speed?
  • AMove JSON files to S3 Express One Zone
  • BIncrease the Athena Workgroup scan limit
  • CLoad data into Redshift for queries
  • DUse Glue ETL to convert JSON to Parquet and store in S3 partitioned by date
✓ Answer: D

Two key optimizations: Parquet (columnar format, only scans needed columns) + date partitioning (querying 7 days scans only 7 directories). This is the most effective way to reduce Athena cost.

A is wrong: S3 Express One Zone doesn't reduce Athena scan volume
B is wrong: Increasing the limit allows more scanning — not cost-saving
C is wrong: Redshift requires cluster maintenance; cost may not be lower
Q03 · Domain 1 Incremental Processing
A Glue ETL Job runs every hour and reads all files from S3. As data grows, the Job gets slower and re-processes already-processed files. How can you solve the duplicate processing problem with minimal changes?
  • ARecord a timestamp in code and filter out old files
  • BEnable Glue Job Bookmark
  • CMove processed files to a different S3 path
  • DSwitch to DynamoDB Streams trigger
✓ Answer: B

Glue Job Bookmark is a native Glue feature that records the last successfully processed position and automatically continues from that checkpoint on the next run. It's a one-click configuration change — minimal modification.

A is wrong: Writing timestamp logic yourself is feasible but more code changes and error-prone
C is wrong: Moving files breaks data lake structure and introduces complexity
D is wrong: DynamoDB Streams doesn't match an S3 file processing scenario
Q04 · Domain 2 Storage Selection
A financial company needs: ① store 10 years of historical transaction data; ② analysts run complex SQL reports daily; ③ data scientists occasionally query raw data; ④ minimize cost. What is the most appropriate architecture?
  • AStore everything in RDS MySQL with regular backups to S3
  • BStore everything in Redshift Serverless
  • CRaw data in S3 (Parquet + partitioned); hot data loaded to Redshift; analysts use Redshift; data scientists use Athena to query S3
  • DStore everything in DynamoDB with Lambda aggregation
✓ Answer: C

Classic Lakehouse architecture: S3 data lake (low cost, Parquet-optimized) + Redshift (high-performance reporting for analysts) + Athena (on-demand S3 queries for data scientists, serverless savings). Redshift Spectrum also lets Redshift query cold S3 data.

A is wrong: RDS MySQL is OLTP — not suitable for complex analytics; 10 years of data would exceed its limits
B is wrong: Storing everything in Redshift has high storage cost
D is wrong: DynamoDB is not suitable for complex SQL aggregations
Q05 · Domain 2 Redshift Optimization
A Redshift cluster has an orders table (10 billion rows) and a customers table (1 million rows) that are frequently JOINed. Queries are slow due to heavy network data transfer. How should you optimize the Distribution Style?
  • AUse EVEN Distribution for both orders and customers
  • BAdd more Redshift cluster nodes
  • CMerge both tables into one wide table
  • DKEY Distribution (customer_id) for orders; ALL Distribution for customers
✓ Answer: D

Large table orders uses KEY (customer_id) → orders with the same customer_id land on the same node; small dimension table customers uses ALL → every node has a full copy. JOINs happen on the same node (Co-located Join), zero network transfer.

A is wrong: EVEN distribution causes heavy network transfer during JOINs
B is wrong: Adding nodes increases capacity but doesn't fix the Distribution design problem
C is wrong: Merging into a wide table causes data redundancy and maintenance complexity
Q06 · Domain 3 Pipeline Orchestration
An ETL pipeline needs: ① extract from RDS; ② Glue transform; ③ load to Redshift; ④ Lambda data quality check; ⑤ SNS alert and stop if quality fails. Error handling and retries are required between steps. Which orchestration service is most appropriate?
  • AEventBridge scheduled triggers, each step independently triggering the next
  • BAWS Step Functions — define a state machine with error handling and retry logic
  • CGlue Workflow chaining all steps
  • DLambda chain calls
✓ Answer: B

Step Functions is designed for stateful workflows: supports all AWS services (Glue/Lambda/SNS); native Retry and Catch error handling; Catch on failure → transition to SNS notification state; visual workflow diagram.

A is wrong: EventBridge has no built-in step state management or error handling
C is wrong: Glue Workflow can only orchestrate Glue components — Lambda and SNS cannot be included
D is wrong: Lambda chaining is tightly coupled, 15-minute timeout, no error state management
Q07 · Domain 3 Monitoring & Troubleshooting
A Kinesis Data Streams IteratorAgeMilliseconds metric has been continuously rising for over an hour — consumers can't keep up with producers. How do you resolve this?
  • AReplace Kinesis Data Streams with SQS FIFO
  • BIncrease Kinesis Data Streams data retention to 7 days
  • CIncrease the number of Shards (Resharding) and increase consumer parallelism
  • DReplace Kinesis Streams with Kinesis Firehose
✓ Answer: C

Rising IteratorAgeMilliseconds = consumption rate < production rate → data backlog. Solution: increase Shard count (raises throughput limit; each Shard: 1MB/s write, 2MB/s read) + increase consumer thread parallelism.

A is wrong: SQS FIFO has throughput limits (300 TPS), unsuitable for high-throughput streaming
B is wrong: Retention time only affects how long data is kept — does not solve consumption speed issues
D is wrong: Firehose is no-code loading; it cannot resolve custom consumer backlog problems
Q08 · Domain 4 Data Governance
An S3 data lake has a user table with PII fields (email, phone). Data engineers can see all columns; analysts can only see masked versions. Both teams query the same Glue Catalog table via Athena. How do you implement this?
  • ACreate two Athena Workgroups, one for each team
  • BCreate two copies of the S3 data (one with PII, one masked), one for each team
  • CUse Lake Formation Column Filter for the analyst role to hide or mask PII columns
  • DGive analysts an IAM Policy that denies reading S3 paths containing PII
✓ Answer: C

Lake Formation supports column-level access control: engineer role gets Grant on ALL columns; analyst role gets Grant on specified columns (excluding PII) or column-level data masking. Only one copy of data exists in S3; visibility is controlled at the query layer.

A is wrong: Workgroups control resource and scan limits — not column-level data access
B is wrong: Duplicate data is redundant, syncing is complex, and cost is high
D is wrong: S3-path-level IAM is too coarse — cannot do column-level differentiation
Q09 · Domain 1 Database Migration
An on-premises Oracle database (2TB) needs to migrate to Aurora PostgreSQL with no more than 1 hour of downtime. What is the most appropriate migration approach?
  • AExport Oracle data directly with pg_dump, then pg_restore to Aurora
  • BShut down, use Snowball to move data to S3, then import from S3 to Aurora
  • CUse only AWS DMS full-load migration
  • DSCT converts Schema, DMS full load + CDC ongoing replication, then cut over when lag is near zero (under 1 hour)
✓ Answer: D

Oracle → Aurora PostgreSQL is a heterogeneous migration. Standard process: SCT converts DDL/stored procedures → DMS full load (business runs normally) → DMS CDC syncs ongoing changes → cut over when CDC lag approaches zero. Total downtime can be kept under 1 hour.

A is wrong: pg_dump does not support Oracle; 2TB requires lengthy downtime
B is wrong: Snowball transfer requires downtime during shipment
C is wrong: Full load only — business keeps running during migration, so there will be data inconsistency at cutover without CDC
Q10 · Domain 4 Encryption & Compliance
S3 stores financial data. Compliance requirements: ① encrypted at rest and keys controlled by the company (auditable and revocable); ② data in transit must also be encrypted. Which configuration should you choose?
  • ASSE-S3 + HTTP access
  • BSSE-S3 + enforce HTTPS Bucket Policy
  • CSSE-KMS (Customer Managed CMK) + enforce HTTPS Bucket Policy
  • DClient-side encryption + HTTP access
✓ Answer: C

Company controls keys → SSE-KMS with Customer Managed CMK (CloudTrail records key usage; you can disable the CMK to revoke access — SSE-S3 keys are fully AWS-managed, which doesn't satisfy this requirement). Transit encryption → enforce HTTPS via Bucket Policy (Deny aws:SecureTransport=false).
