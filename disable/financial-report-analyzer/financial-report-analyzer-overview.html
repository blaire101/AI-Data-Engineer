Financial Report Analyzer

End-to-end AWS pipeline that ingests annual and quarterly PDF reports, extracts ~3,000 sentences using Amazon Textract, and applies a two-stage NLP system to identify the top-3 supporting sentences per financial metric — complete with confidence scores.

What it does
Problem being solved

Analysts at DBS, Credit Suisse, and BCA spend hours manually reading annual reports to extract evidence for each financial metric — revenue, EBITDA, depreciation, and so on. This system automates that process end-to-end: a PDF goes in, a structured analysis report with cited supporting sentences and page references comes out.

Output example

For the metric "Sales", the system outputs: the computed value ($232.9 billion, up 30.9% year-over-year), plus the three sentences from the report that best support this figure — each tagged with a page number and a confidence score. For example: "Sales increased 31% in 2017 and 2018" (page 31, score: 0.9883).

Clients and scale

Deployed for DBS, Credit Suisse, and BCA. Processes both annual and quarterly reports across multiple companies and years. The pipeline is fully automated — once a PDF is uploaded, no human intervention is required until the final report is ready in S3.

AWS services used
Data Engineering layer

API Gateway receives PDF uploads. S3 stores raw PDFs and processed Parquet files, partitioned by company and year. Amazon Textract extracts structured text from the PDF — approximately 3,000 sentences per report. OpenSearch indexes all sentences for full-text BM25 search in Stage 1. Step Functions orchestrates the two-stage NLP pipeline, running all financial metrics in parallel with a concurrency limit of 5. Lambda functions handle each individual processing step. Results are assembled by a final Lambda and written back to S3 as both a markdown report and a structured JSON file.

Machine Learning layer

A Keras BiLSTM text classifier trained on financial report sentences. The trained model is packaged as a tar.gz file, uploaded to S3, and deployed as a SageMaker Endpoint using TensorFlowModel. Inference runs on an ml.m5.xlarge CPU instance — no GPU required for BiLSTM inference at this scale. Lambda calls the endpoint via invoke_endpoint, passing 100 candidate sentences and receiving confidence scores back.

Infrastructure as code

Terraform manages the S3 buckets, IAM roles with least-privilege permissions, Lambda function deployments, the S3-to-Lambda trigger, and the Step Functions state machine. The SageMaker endpoint is deployed separately via the SageMaker Python SDK, since model updates happen independently of infrastructure changes.

System Design

End-to-end pipeline

Six stages, fully automated. A PDF goes in — a structured analysis report comes out.

1
Ingestion
API Gateway → S3 raw bucket
User uploads a PDF via the web API. API Gateway validates the request and the ingestion Lambda writes the file to S3 with metadata — company name, year, and report type (annual or quarterly) embedded in the S3 key path.
2
Parsing
Amazon Textract → ~3,000 sentences
An S3 ObjectCreated event triggers the parsing Lambda. It calls Amazon Textract to extract all text blocks from the PDF — typically around 3,000 sentences per annual report. Each sentence is tagged with its page number and a Textract confidence score. Results are written to S3 in Parquet format (partitioned by company and year) and bulk-indexed into OpenSearch for Stage 1 retrieval.
3
Stage 1 — Keyword Retrieval
OpenSearch BM25 + TF-IDF → 100 candidates
For each financial metric — sales, EBITDA, depreciation, interest expense, and so on — Stage 1 runs a BM25 full-text search against OpenSearch using a predefined keyword dictionary. The initial results are then re-ranked using TF-IDF cosine similarity within Lambda. This narrows approximately 3,000 sentences down to 100 high-probability candidates per metric. Step Functions runs all metrics in parallel with a concurrency limit of 5.
4
Stage 2 — Text Classification
SageMaker Endpoint (Keras BiLSTM) → Top-3
The Stage 2 Lambda sends the 100 candidate sentences to the SageMaker Endpoint, which hosts the trained Keras BiLSTM classifier. The model assigns each sentence a probability of being "highly relevant" to the target metric. The Lambda sorts by confidence score and returns the top 3 — each with its sentence text, page number, and probability score. Accuracy 0.797, Macro F1 0.737.
5
Assembly
Top-3 + field values → report.md + result.json
The assembly Lambda collects the Top-3 supporting sentences for every metric along with the computed financial values — for example, Sales equals $232.9 billion, up 30.9% year-over-year. It merges these into two output formats: a structured JSON file matching the internal token schema, and a human-readable markdown report with computed values, directional language, and cited evidence sentences including page numbers and scores.
6
Storage
S3 processed bucket → analysts
Both output files are written to the S3 processed bucket, partitioned by company and year. Analysts at DBS, Credit Suisse, and BCA access the final markdown report. The structured JSON is available for downstream systems or further programmatic analysis via Athena.
Machine Learning

Keras BiLSTM Classifier

Text classification model that identifies which sentences in a financial report support a given metric movement.

Model design
Architecture

Bidirectional LSTM — the model reads each sentence both forward and backward, capturing context from both directions. The embedding layer converts words to dense vectors. The BiLSTM layer produces a hidden representation by concatenating the final forward and backward hidden states. A dropout layer reduces overfitting. The output Dense layer produces probabilities across three classes: not relevant, relevant, and highly relevant.

Training task

The model is trained as a three-class sentence classifier. Given a sentence and a target financial metric — for example, "sales" — the model predicts whether the sentence is not relevant, relevant, or highly relevant to explaining the movement of that metric. Training data consisted of manually labelled sentences from historical annual reports across multiple companies and years.

Performance

Accuracy 0.797 and Macro F1 0.737 on the held-out test set. Macro F1 is the primary metric because the three classes are not perfectly balanced — highly relevant sentences are rarer than not-relevant ones, so a model that simply predicts the majority class would score well on accuracy but poorly on Macro F1.

Deployment on AWS
Step 1 — Save and package

After training, the Keras model is saved in SavedModel format using model.save(). The vocabulary dictionary — which maps each word to its token index — is saved as a JSON file alongside the model. Both files are packaged into a single tar.gz archive, which is the format SageMaker requires.

Step 2 — inference.py

SageMaker requires an inference.py file that defines four functions: model_fn loads the model and vocab from disk when the endpoint starts; input_fn parses the incoming JSON request from Lambda; predict_fn tokenizes the sentences, pads them to a fixed length of 64 tokens, runs them through the BiLSTM, and applies softmax to get class probabilities; output_fn serializes the results back to JSON.

Step 3 — Deploy endpoint

The tar.gz is uploaded to S3 using boto3. A TensorFlowModel object is created with the S3 URI, the IAM role, the inference.py entry point, and the TensorFlow framework version. Calling dot deploy() provisions an ml.m5.xlarge instance, downloads the model, starts the inference server, and registers a named endpoint. From that point, Lambda can call invoke_endpoint to send sentences and receive confidence scores.

Interview Prep

Expected Q&A

Likely questions about this project in a Data Engineering or ML interview.

Data Engineering
🗂️
Why store sentences in OpenSearch and also in S3 Parquet — isn't that redundant?
Storage
▼

They serve completely different purposes. OpenSearch is the retrieval engine for Stage 1 — it runs BM25 full-text search at query time, which requires an inverted index that S3 Parquet cannot provide. S3 Parquet is the long-term analytical store — it lets Athena run SQL aggregations across all documents, partitioned by company and year, at much lower cost than querying OpenSearch for bulk analytics. OpenSearch is optimised for low-latency search; S3 Parquet is optimised for cost-efficient batch analysis. Storing in both is the standard lambda architecture pattern, not redundancy.

⚡
Why Step Functions instead of just chaining Lambda calls?
Orchestration
▼

Three reasons. First, there are around 11 financial metrics per report, and each metric needs Stage 1 followed by Stage 2. Chaining those inside a single Lambda would hit the 15-minute timeout limit on large reports. Step Functions' Map state runs all metrics in parallel and manages the fan-out automatically. Second, Step Functions provides built-in retry logic — if Stage 2 fails for one metric, it can retry that metric without restarting the entire pipeline. Third, the execution history is fully visible in the AWS console, which makes debugging a failed run much faster than parsing CloudWatch logs from multiple chained Lambda calls.

📦
Why Parquet and not JSON for the S3 processed bucket?
Storage format
▼

Athena charges per byte scanned. Parquet is columnar, so a query that only reads the "text" and "page" columns does not scan the "confidence" or "word_count" columns at all. Parquet with Snappy compression is typically three to five times smaller than equivalent JSON, which directly reduces Athena query cost. The partition scheme — company equals amazon, year equals 2026 — means a query for one company's one year of data scans only that partition, not the entire dataset. JSON would require scanning every byte of every file for every query regardless of which columns are needed.

🔐
How is access controlled — who can read the financial reports?
Security
▼

Every Lambda function has its own IAM role with the minimum permissions it needs — the ingestion Lambda can only write to the raw S3 bucket, the parsing Lambda can read the raw bucket and write to the processed bucket, and the Stage 2 Lambda can only invoke the SageMaker endpoint plus read and write its specific S3 paths. No Lambda has wildcard resource permissions. Both S3 buckets block all public access. The SageMaker endpoint is only reachable via the IAM role attached to the Stage 2 Lambda — it is not exposed via a public HTTPS URL.

Machine Learning
🧠
Why BiLSTM for this task — why not a transformer like BERT?
Model choice
▼

At the time of the project, BiLSTM was a strong baseline for sentence classification tasks and significantly cheaper to train and serve than BERT. The inference latency on an ml.m5.xlarge CPU instance is well within acceptable bounds for this batch pipeline — BERT on a CPU instance would be considerably slower per sentence. The financial domain vocabulary is relatively constrained, and the BiLSTM achieved 0.797 accuracy which met the product requirement. A transformer would likely improve Macro F1, but at the cost of a GPU instance for serving, which was not justified given the current accuracy threshold.

📊
Why Macro F1 as the evaluation metric rather than accuracy?
Evaluation
▼

The three classes are imbalanced. In a typical annual report, most sentences are not relevant to any specific metric, a smaller number are relevant, and a very small number are highly relevant. A model that predicts "not relevant" for every sentence would achieve high accuracy simply because the majority class dominates. Macro F1 averages the F1 score across all three classes equally, regardless of class frequency — so a model must perform well on the rare "highly relevant" class, which is the class that actually matters for producing correct evidence sentences in the final report.

🔄
How do you update the model without downtime?
MLOps
▼

SageMaker supports blue-green deployment for endpoint updates. When a new model version is trained, it is packaged and uploaded to S3 as a new tar.gz. A new model object is created pointing at the new S3 URI. Calling update_endpoint on the existing endpoint name triggers SageMaker to provision new instances with the new model, wait until they pass health checks, then shift traffic from the old instances to the new ones. The old instances are only terminated after traffic has fully switched. This means the endpoint stays available throughout the update with no downtime window.

Engineering Challenges

Problems encountered

Real issues hit during development and how they were resolved.

Parsing Textract returning fragmented sentences across LINE blocks ▼
Problem
Textract's LINE blocks do not always correspond to complete sentences. A single sentence split across two lines in the PDF would come back as two separate LINE blocks — "Sales increased 31% in 2017" and "and 2018, compared to the comparable prior years." — which breaks the classifier because it was trained on full sentences.
Solution
Added a post-processing step in the parsing Lambda that merges consecutive LINE blocks on the same page if the previous block does not end with a sentence-terminating character — period, exclamation mark, or question mark. This recovers most split sentences without requiring expensive re-parsing. The merged result is what gets indexed into OpenSearch and stored in Parquet.
SageMaker Model loaded on SageMaker but inference results differed from local test ▼
Problem
Local test_local.py produced confidence scores around 0.98 for the top sentences. The same sentences sent to the SageMaker endpoint returned scores around 0.45 — completely different. The endpoint was running the right model file but producing wrong predictions.
Root cause
The vocab.json was not included in the model.tar.gz. SageMaker's model_fn was falling back to an empty dictionary, mapping every word to the unknown token index. The model was running, but on a sequence of all-unknown-token inputs — which explains why it produced plausible-looking but completely wrong probabilities rather than crashing.
Fix
Added vocab.json to the tarball in save_model.py and added an explicit assertion in model_fn that raises an error if the loaded vocab has fewer than 100 entries — which would have surfaced the problem immediately at endpoint startup rather than silently returning wrong scores.
Step Functions Step Functions Map state timeout on large reports ▼
Problem
For large annual reports with many metrics running in parallel, the Step Functions execution was hitting the Lambda concurrency limit for the account, causing some Stage 2 invocations to be throttled and eventually timing out.
Solution
Set MaxConcurrency to 5 on the Map state, which limits how many metric branches run simultaneously. Added retry configuration on the Stage 2 task with exponential backoff — up to 3 retries with a 2-second initial interval. Also reserved concurrency on the Stage 2 Lambda to guarantee it always has capacity available, preventing it from being crowded out by other functions in the same account.
OpenSearch OpenSearch bulk indexing failing silently on large batches ▼
Problem
The parsing Lambda reported successful indexing but some sentences were missing from OpenSearch search results. The bulk call returned without raising an exception even though some documents had failed to index due to a mapping conflict on the "confidence" field — Textract sometimes returns a string, sometimes a float.
Solution
Two changes. First, explicitly cast the confidence field to float before indexing — removing the type ambiguity at source. Second, changed the helpers.bulk call to raise_on_error equals True and log the full errors list when it is non-empty. This surfaced the mapping conflict immediately on the next run instead of silently dropping documents. Also defined an explicit index mapping in OpenSearch so type conflicts are caught at index creation time rather than at document ingestion time.
Class imbalance Model predicting "not relevant" for almost everything ▼
Problem
Early training runs produced a model with high accuracy but very low Macro F1 — around 0.4. Inspection showed the model was predicting class 0 (not relevant) for nearly all inputs. The training data had severe class imbalance: roughly 80% not relevant, 15% relevant, 5% highly relevant.
Solution
Applied class weights during training — the highly relevant class received a weight approximately 16 times higher than the not relevant class, forcing the model to penalise misclassifying rare positive examples more heavily. Also used stratified sampling to ensure every training batch contained examples from all three classes. These two changes together pushed Macro F1 from 0.4 to 0.737 while keeping accuracy at 0.797.
