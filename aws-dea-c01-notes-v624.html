域1 摄取&变换 34% — 核心考点
  • Kinesis Data Streams（实时）vs Firehose（近实时入库）vs MSK（Kafka托管）
  • Glue ETL Job（Serverless Spark）vs DataBrew（可视化无代码）
  • AWS DMS：同构/异构迁移，CDC 持续捕获变更
  • 批量摄取：S3 + Glue Crawler + Athena CTAS
  • 格式转换：CSV/JSON → Parquet/ORC（列式更高效）
  • Glue Job Bookmark：增量处理，不重复读取
  • AppFlow：SaaS 数据源（Salesforce）→ S3
  • EventBridge / Lambda 触发 Glue Job 调度
域2 存储管理 26% — 核心考点
  • Redshift：OLAP列式数仓，Distribution Style 和 Sort Key
  • S3 数据湖：分区策略，Parquet 格式最优
  • Lake Formation：细粒度权限（列级/行级），Data Catalog
  • Glue Data Catalog：Crawler 自动扫描 Schema
  • Redshift Spectrum：直接查询 S3（无需加载）
  • Athena：Serverless SQL on S3，按扫描量计费
  • EMR：Hadoop/Spark 集群，PB 级大数据处理
  • DynamoDB：高频点查，毫秒延迟，自动扩展
域3 运维支持 22% — 核心考点
  • Step Functions：有状态工作流，含错误处理和重试
  • MWAA（Managed Airflow）：复杂 Python DAG 调度
  • CloudWatch：监控 Glue/Kinesis/EMR，告警触发 SNS
  • Glue Job 故障：DPU 不足，数据倾斜，Job Bookmark
  • Glue Data Quality：DQ 规则内嵌 ETL 流程
  • Redshift 查询优化：VACUUM，ANALYZE，WLM
  • Kinesis 扩容：IteratorAgeMilliseconds 升高 → 加 Shard
  • EMR Transient Cluster：任务完成自动关闭省钱
域4 安全治理 18% — 核心考点
  • Lake Formation：数据湖统一权限（列级/行级 Grant）
  • KMS CMK：S3/Redshift/Glue/Kinesis 静态加密
  • IAM Role：Glue/EMR/Lambda 访问资源的权限
  • Macie：识别 S3 中的 PII 数据
  • Redshift RLS + 动态数据遮蔽（DDM）
  • CloudTrail：审计所有 API 调用日志
  • VPC Endpoint：Glue/Kinesis/S3 私有访问不走公网
  • AWS Config：配置变更追踪，合规规则自动检测

Glue 全家桶（DEA-C01 最核心服务）
Glue ETL Job
  • Serverless Spark 分布式计算
  • Python Shell 或 PySpark 脚本
  • DPU 配置决定并行度和成本
  • Job Bookmark：记录处理位置，增量加载
  • JDBC 连接数据库
  • Dynamic Frames（Glue 特有数据结构）
关键词：large-scale ETL, Spark, DPU, incremental
Glue Data Catalog
  • 统一元数据仓库（Schema/表结构）
  • Crawler 自动扫描 S3/RDS/Redshift
  • Athena / Redshift Spectrum / EMR 共用
  • 替代 Hive Metastore
  • 跨账号共享（Resource Policy）
关键词：metadata, schema, crawler, catalog
Glue DataBrew
  • 可视化数据清洗（无代码）
  • 250+ 内置变换配方（Recipe）
  • 数据分析：列统计、缺失值检测
  • 适合数据分析师（非工程师）
  • 输出到 S3 / Redshift
关键词：no-code, visual, recipe, data profile
Glue ETL vs DataBrew vs EMR：代码化大规模 Spark → Glue ETL；可视化无代码清洗 → DataBrew；需要完整 Hadoop 生态/自定义框架/长期集群 → EMR。

AWS DMS 数据迁移
  • 全量迁移一次性迁移历史数据，业务停止期间进行
  • CDC（持续复制）捕获源库变更，实时同步到目标（如 Redshift）
  • 同构迁移MySQL→MySQL，只用 DMS 即可
  • 异构迁移Oracle→Aurora，需要 SCT 转 Schema + DMS 迁数据
  • Replication InstanceDMS 的计算节点，需选合适大小
  • 常见目标Redshift / S3 / DynamoDB / Aurora / OpenSearch
DEA 高频场景：on-premises DB → Redshift（DMS CDC 持续同步）；Oracle → Aurora（SCT + DMS 组合）。

Redshift 深度考点

Distribution Style（数据分布方式）

  • AUTO自动选择，小表ALL，大表KEY，新手推荐
  • EVEN轮询均匀分布，无Join场景，防数据倾斜
  • KEY按指定列分布，Join时同列数据在同节点，减少网络传输
  • ALL每节点一份完整数据，适合小维度表（Join优化）
大表Join经典方案：大表用 KEY（customer_id），小维表用 ALL，Co-located Join 零网络传输。

其他关键特性

  • Sort Key决定数据在磁盘上的排列，加速范围查询
  • WLMWorkload Management，按用户组分配查询资源
  • COPY 命令从 S3 批量加载，最快方式（并行）
  • UNLOADRedshift → S3 导出，可指定 Parquet 格式
  • Materialized Views预计算结果，加速重复聚合查询
  • Spectrum查询 S3 外部表，冷热数据分离架构
  • Serverless按 RPU 小时计费，无需管理集群
Athena 查询优化（成本+性能）
  • 使用 Parquet/ORC列式格式，只扫描需要的列，最有效降成本
  • 分区（Partitioning）按 year/month/day 分区，WHERE 跳过无关分区
  • CTAS查询结果写成 Parquet 新表，加速后续查询
  • Workgroup控制扫描量上限，防止团队超额费用
  • Federated Query跨数据源查询（RDS/DynamoDB）via Lambda Connector
  • MSCK REPAIR TABLE更新 Glue Catalog 分区，Athena 才能发现新分区
Athena 按扫描 GB 计费：Parquet + 分区 = 省钱 + 加速的最优组合。
Lake Formation 权限控制
  • Data Catalog统一元数据（由 Glue Crawler 填充）
  • 数据库级 Grant授予某角色访问整个数据库
  • 表级 Grant授予某角色访问特定表
  • 列级 Filter对特定角色隐藏或脱敏某些列（PII保护）
  • 行级 Filter对特定角色只展示满足条件的行
  • IAM + LF 双验证两者都必须允许才能访问，任一拒绝即失败
Lake Formation 权限模型：IAM Policy 和 Lake Formation Grant 必须同时满足！不是只配一个就够的。

EMR 集群配置要点

节点类型

  • Master Node管理集群，YARN/HDFS NameNode，必须 On-Demand
  • Core Node运行任务+存 HDFS，尽量 On-Demand
  • Task Node只运行任务，不存 HDFS，可用 Spot（省 90%）

存储选择

  • EMRFS（S3）推荐，持久化，集群关闭数据不丢
  • HDFS（本地）高性能但临时，集群关闭数据丢失
  • EBS本地磁盘，中间计算结果

成本优化

  • Transient Cluster任务完成自动关闭，按需付费
  • Task Node SpotTask Node 用 Spot 省 70-90%
  • Instance Fleet混合多种实例类型，提高 Spot 可用性
EMR Task Node 用 Spot 是最佳实践：Task Node 不存 HDFS 数据，Spot 被回收只是任务重试，数据安全在 S3（EMRFS）。

Q01 · 域1 实时流处理
电商平台需要实时分析用户点击流（每秒 50000 条），计算每分钟热门商品 Top10，结果写入 DynamoDB 供 API 查询。最合适的架构？
  • AKinesis Firehose → S3 → Glue ETL（每小时触发）→ DynamoDB
  • BSQS → Lambda（每分钟触发）→ DynamoDB
  • CKinesis Data Streams → Kinesis Data Analytics (Flink) 窗口聚合 → Lambda → DynamoDB
  • DMSK → EMR Spark Streaming → Redshift
✓ 答案：C

需求：实时处理（毫秒级）+ 窗口聚合（每分钟Top10）+ 低延迟查询（DynamoDB）。
Kinesis Data Streams 接收高吞吐实时数据 → Kinesis Data Analytics (Flink) 做滑动窗口聚合 → Lambda 写入 DynamoDB。

A 错：Firehose 有 60 秒 buffer，Glue 每小时触发，都不是真正实时
B 错：SQS 无法做流式窗口聚合，Lambda 定时触发也非实时
D 错：MSK+EMR 重量级，Redshift 不适合 API 低延迟点查询
Q02 · 域1 格式优化
大量 JSON 日志存在 S3，Athena 查询很慢且费用高。分析师每天只查最近 7 天数据。如何最有效降低成本和提升速度？
  • A把 JSON 文件移到 S3 Express One Zone
  • B增加 Athena Workgroup 的扫描限额
  • C把数据加载到 Redshift 查询
  • D用 Glue ETL 把 JSON 转换为 Parquet 并按日期分区存 S3
✓ 答案：D

两个关键优化：Parquet（列式格式，只扫描需要的列）+ 日期分区（查7天只扫7天目录）。这是降低 Athena 成本最有效的手段。

A 错：S3 Express One Zone 不解决 Athena 扫描量问题
B 错：增加限额反而允许更多扫描，不省钱
C 错：Redshift 需维护集群，成本不一定低
Q03 · 域1 增量处理
Glue ETL Job 每小时运行，从 S3 读取所有文件处理。随着数据增多，Job 越来越慢且重复处理已处理的文件。如何以最小改动解决重复处理问题？
  • A在代码中记录时间戳，过滤旧文件
  • B启用 Glue Job Bookmark 功能
  • C处理完后把文件移动到另一个 S3 路径
  • D改为 DynamoDB Streams 触发
✓ 答案：B

Glue Job Bookmark 是 Glue 原生功能，记录上次成功处理的位置，下次自动从断点继续。在 Job 配置中一键启用，最小改动。

A 错：自己写时间戳逻辑可以实现但改动大易出错
C 错：移动文件破坏数据湖结构，引入复杂性
D 错：DynamoDB Streams 与 S3 文件处理场景不匹配
Q04 · 域2 存储选型
金融公司需要：①存储10年历史交易数据；②分析师每天运行复杂SQL报表；③数据科学家偶尔查原始数据；④成本尽量低。最合适的架构？
  • A全部存在 RDS MySQL，定期备份到 S3
  • B全部存在 Redshift Serverless
  • C原始数据存 S3（Parquet+分区），热数据加载到 Redshift；分析师用 Redshift，数据科学家用 Athena 查 S3
  • D全部存在 DynamoDB，Lambda 聚合
✓ 答案：C

经典湖仓架构（Lakehouse）：S3 数据湖（成本低，Parquet 优化）+ Redshift（分析师高性能报表）+ Athena（数据科学家按需查 S3，Serverless 省钱）。Redshift Spectrum 还可让 Redshift 查询 S3 冷数据。

A 错：RDS MySQL 是 OLTP，不适合复杂分析，10年数据量也撑不住
B 错：全部在 Redshift 存储成本高
D 错：DynamoDB 不适合复杂 SQL 聚合
Q05 · 域2 Redshift 优化
Redshift 集群有 orders 表（100亿行）和 customers 表（100万行），经常需要 JOIN。查询时大量网络数据传输导致很慢。如何优化 Distribution Style？
  • Aorders 和 customers 都用 EVEN Distribution
  • B增加 Redshift 集群节点数量
  • C把两张表合并成一张宽表
  • Dorders 用 KEY Distribution（customer_id），customers 用 ALL Distribution
✓ 答案：D

大表 orders 用 KEY（customer_id）→ 相同 customer_id 的订单在同一节点；小维表 customers 用 ALL → 每个节点都有一份。JOIN 时数据在同一节点（Co-located Join），零网络传输。

A 错：EVEN 分布 JOIN 时需要大量网络传输
B 错：加节点提高容量，不解决 Distribution 设计问题
C 错：合并宽表数据冗余，维护复杂
Q06 · 域3 Pipeline 编排
ETL Pipeline 需要：①从 RDS 提取；②Glue 变换；③加载 Redshift；④Lambda 数据质量检查；⑤质量失败时 SNS 告警停止。需要步骤间错误处理和重试。最合适的编排服务？
  • AEventBridge 定时触发，每步独立触发下一步
  • BAWS Step Functions，定义含错误处理和重试逻辑的状态机
  • CGlue Workflow 串联所有步骤
  • DLambda 链式调用
✓ 答案：B

Step Functions 专为有状态工作流设计：支持 Glue/Lambda/SNS 等所有 AWS 服务；原生 Retry 和 Catch 错误处理；Catch 失败 → 转到 SNS 告警状态；可视化工作流图。

A 错：EventBridge 无内置步骤间状态管理和错误处理
C 错：Glue Workflow 只能编排 Glue 组件，Lambda 和 SNS 无法加入
D 错：Lambda 链式耦合紧，15 分钟超时，无错误状态管理
Q07 · 域3 监控故障
Kinesis Data Streams 的 IteratorAgeMilliseconds 指标持续升高超过 1 小时，消费者跟不上生产者。如何解决？
  • A把 Kinesis Data Streams 换成 SQS FIFO
  • B增加 Kinesis Data Streams 的数据保留时间到 7 天
  • C增加 Shard 数量（Resharding），同时增加消费者并行度
  • D把 Kinesis Streams 换成 Kinesis Firehose
✓ 答案：C

IteratorAgeMilliseconds 升高 = 消费速度 < 生产速度，数据积压。解决：增加 Shard 数（提升吞吐上限，每 Shard 1MB/s写 2MB/s读）+ 增加消费者线程。

A 错：SQS FIFO 有吞吐限制（300 TPS），不适合高吞吐流场景
B 错：保留时间只影响数据存多久，不解决消费速度问题
D 错：Firehose 是无代码入库，无法解决自定义消费的积压问题
Q08 · 域4 数据治理
S3 数据湖的用户表有 PII 字段（email, phone）。数据工程师可以看所有列，分析师只能看脱敏版本。两个团队都用 Athena 查询同一张 Glue Catalog 表。如何实现？
  • A创建两个 Athena Workgroup 分别给两个团队
  • B创建两份 S3 数据（一份有 PII，一份脱敏），分别给两个团队
  • CLake Formation 对分析师角色设置列过滤（Column Filter），隐藏或脱敏 PII 列
  • D给分析师 IAM Policy 拒绝读取包含 PII 的 S3 路径
✓ 答案：C

Lake Formation 支持列级权限控制：工程师角色 Grant ALL columns；分析师角色 Grant 指定列（排除 PII）或设置列级数据遮蔽。底层 S3 只有一份数据，在查询层控制可见性。

A 错：Workgroup 控制资源和扫描限额，不控制列级数据访问
B 错：两份数据冗余，同步复杂，成本高
D 错：S3 路径级 IAM 太粗，无法做列级区分
Q09 · 域1 数据库迁移
on-premises Oracle 数据库（2TB）需要迁移到 Aurora PostgreSQL，停机时间不超过 1 小时。最合适的迁移方案？
  • A直接用 pg_dump 导出 Oracle 数据，pg_restore 导入 Aurora
  • B停机后用 Snowball 把数据迁到 S3，再从 S3 导入 Aurora
  • C只用 AWS DMS 全量迁移
  • DSCT 转换 Schema，DMS 全量迁移 + CDC 持续同步，零延迟后停机切换（不超过 1 小时）
✓ 答案：D

Oracle → Aurora PostgreSQL 是异构迁移，标准流程：SCT 转换 DDL/存储过程 → DMS 全量（业务运行期间）→ DMS CDC 持续同步增量 → CDC 延迟接近零时停机切换。整个停机时间可控制在 1 小时内。

A 错：pg_dump 不支持 Oracle，2TB 需要长停机
B 错：Snowball 传输期间需停机
C 错：只全量时业务仍在跑，切换时数据不一致，还需要 CDC
Q10 · 域4 加密合规
S3 存储财务数据，合规要求：①加密存储且密钥由公司控制（可审计可撤销）；②传输中也必须加密。应选哪种配置？

Q11 · 域3 EMR 成本优化（多选）
EMR 每晚运行 Spark 批处理（约4小时），处理 S3 数据结果写回 S3，白天集群空闲。如何最大化节省成本？（选2个）
  • A使用常驻集群（Always-On），避免每晚重启时间
  • B使用 Transient（临时）集群，任务完成后自动终止
  • C所有节点（Master/Core/Task）购买 Reserved Instance
  • DTask Node 用 Spot Instance，Core Node 用 On-Demand，数据存在 S3（EMRFS）
✓ 答案：B + D

B（Transient Cluster）：任务完成自动关闭，只付 4 小时费用，不付白天空闲费用。
D（Task Node Spot）：Task Node 不存 HDFS，Spot 被回收时任务重试但数据在 S3 安全，省 70-90% 计算成本。

A 错：常驻集群白天空闲仍收费，非常浪费
C 错：每晚才用的集群买 RI 不划算（RI 适合 7x24 常驻）
Q12 · 域2 第三方数据
金融公司需要把第三方市场数据（股价、经济指标）集成到自己的 S3+Athena 分析平台。第三方通过订阅 API 提供数据，要求最少运维开销。如何实现？
  • A自己写 Lambda 定时调用第三方 API，结果存 S3
  • B让第三方直接推送到公司 Kinesis Data Streams
  • C使用 AWS Data Exchange 订阅第三方数据集，自动交付到 S3
  • D使用 AWS Transfer Family 从第三方 SFTP 拉取文件
✓ 答案：C

AWS Data Exchange 是 AWS 数据市场，提供数千个第三方数据集（金融/气象/医疗等）。订阅后数据自动定期交付到 S3，无需维护 API 调用代码，与 S3+Athena+Redshift 原生集成，"最少运维开销"的最优解。

A 错：自己写 Lambda 需维护代码、错误处理、重试，运维开销高
B 错：让第三方推送需对方支持，安全配置复杂
